## Gotchas
- **"Is this figure in the paper" is near-useless for small integers — and the cause
  is the in-text markers, not the bibliography.** Every integer 0–37 appeared
  somewhere in paper 001. Removing the reference section alone leaves that at 37,
  exactly unchanged; removing the 49 `[n]` markers in the body takes it to 4.
  Measured 2026-09-20, after an earlier note in this file asserted the opposite.
  `source.body_pages` strips the apparatus, `source.citation_band` derives the
  remaining range per paper, and the prose check skips integers inside it.
- **Narrowing that band without word matching ships a false alarm.** Paper 001 writes
  *"Seven coronal plane angles"* and the digit 7 is nowhere in its body, so a deck
  truthfully saying "7 angles" would be called fabricated. `source.find_number_word`
  covers zero–twenty plus the round tens; absence now means absent in both forms.
- **The page extractor leaves a soft hyphen (U+00AD) at every line-break
  hyphenation**, so "tenderness" arrives as `ten<U+00AD> derness` and `\bten\b`
  matches inside it. Any word-level search over page text must de-hyphenate first —
  `source.dehyphenate`. Found by measurement; it made "ten" look present in a paper
  that never uses the word.
- **Two number-matching rules on purpose.** `find_number` is exact (a table cell
  writing 83.9 for the paper's 83.89 is a real misquote). `find_number_rounded` is
  prose-only and rounds at the claim's precision (a deck writing "avg age 19.6" for
  19.59 is correct). Using the rounded one on a table would ship the misquote —
  measured both ways. Do not merge them.
- **`ForcePlate_DecisionSystem/data/forceplate.db` is a DuckDB file, not SQLite.**
  Opening it with `sqlite3` raises `file is not a database`, which is almost certainly
  all "ForcePlate broken on Windows" ever meant. `duckdb.connect(..., read_only=True)`
  opens it fine: 4 tables, 1.25M rows in `raw_tests`. Check the magic bytes before
  believing a database is corrupt — this one says `DUCK` at offset 8.
- **A Git Bash path like `/g/My Drive/...` is not a path Python can open.** `find`
  accepts it and `openpyxl` raises `FileNotFoundError` on the same string. Use the
  Windows form `G:\My Drive\...` in Python, the MSYS form in shell tools.
- **`except BaseException` around `sys.exit(main())` catches the `SystemExit` that
  `sys.exit` itself raises**, so a fail-open wrapper logs an error on every *successful*
  run and buries the real failures. Compute the exit code inside the `try`, call
  `sys.exit` outside it. Caught by reading the log, which is the argument for having
  one: the bug is invisible from the hook's behaviour, since it exits 0 either way.
- **A `UserPromptSubmit` hook must never exit non-zero**: exit 2 blocks the prompt.
  Fail open means empty stdout and exit 0, always. Watch module-scope code: anything
  parsed at import time (an `int()`/`float()` over an env var) runs before the handler
  in `__main__` exists and can exit non-zero on its own.
- **`urllib`'s `timeout=` is NOT a total deadline.** It applies per blocking socket
  operation, so DNS, connect, TLS and every body read each get the whole value. A
  server trickling one byte at a time never trips it. For a real wall-clock bound, run
  the request on a daemon thread and `join(remaining)`; the daemon flag is what lets
  the process exit while the socket is still wedged.
- `~/.claude/hooks/hooks.json` is NOT live. It carries a full `UserPromptSubmit` block
  (`TheRouter.hook.ts` and friends, bun-based, with Mac paths), but nothing in
  `settings.json` references it. Do not assume a hook runs because it is written down.
- `~/.zshenv` is the right profile file, not `~/.zshrc`. Only `.zshenv` is sourced for
  non-interactive shells, which is what Claude Code's Bash tool spawns.
- `security add-generic-password -A` lets any process running as you read the item with
  no GUI prompt. Without it, a non-interactive read can raise a blocking dialog and hang
  the shell. This is the same practical threat model as a `chmod 600` file.
- A restart of Claude Code matters only for things that inherit Claude Code's own
  environment, such as the plugin / MCP processes. The Bash tool does NOT need it:
  it spawns a fresh zsh, which sources `~/.zshenv` and picks the key up. Verified
  2026-09-19 with `env -i HOME="$HOME" USER="$USER" /bin/zsh -c 'echo ${TYPESAFE_API_KEY:+set}'`
  -> `set`. Pass `USER`: the `.zshenv` line calls `security ... -a "$USER"`.
- **The key needs its `apikey_` prefix.** The console shows `apikey_<36>_<64>`, 108 characters
  total. Pasting only the part after `apikey_` returns a clean `401 authentication_error` from
  `POST https://api.typesafe.ai/v1/systemone`. A malformed request body returns 422 instead,
  so 401 means the key value is wrong and 422 means your request is wrong. That split is the
  fastest way to tell which end is at fault.
- **Windows home for the key is `~/.claude/typesafe.env`**, one line,
  `TYPESAFE_API_KEY=apikey_...`. That path is auto-gitignored by the dotclaude whitelist
  (`.gitignore` line 5 is `/*`, so any new top-level file there is ignored), and Claude reads
  it directly with no restart.
- **`~/.bashrc` is NOT sourced by Claude Code's Bash tool on Windows.** Tested with a probe
  export: not visible in a fresh tool shell. Do not put env vars there expecting the agent to
  see them.
- **Windows user environment variables ARE inherited** by the agent's shell, so
  `setx NAME "value"` plus a Claude Code restart also works. That is how `FIREFLIES_API_KEY`
  and the GitHub PAT already reach it. Use it if you want the variable set automatically
  rather than read from a file.
- **`.claude/` is gitignored here.** Claude Code puts per-project worktrees in
  `.claude/worktrees/`, so without the ignore a `git add -A` would commit a whole nested
  checkout. A locked worktree (`jev-docs-capability-map`) was live in there on 2026-09-19.
- On Windows, `git worktree remove` and `git worktree prune` often fail with
  "Permission denied" on the first try because of a transient file lock. A plain `rm -rf` of
  the same path immediately afterwards succeeds. Remove the directory, then the matching
  entry under `.git/worktrees/`.
- Verified 2026-09-19 on Windows against the live API: on a hamstring-tightness note, Noul
  0.9 for "possible injury", Choice "lower body", Score 1.69 across
  ["monitor only", "modify training", "hold out"]. All three primitives return sane values.

# Jev capability map

What TypeSafe's System One model (Jev) can and cannot do, and where it fits the work
we already run. Written 2026-09-19 after reading the full doc set. The vendor mirror in
`docs/vendor/typesafe/` is the reference; this file is the judgment.

## Jev in one screen

Jev is not a small LLM. It does not generate text at all. You send it a **state** (a
string, JSON object, or array) and a map of typed **questions**, and it returns typed
answers with calibrated probabilities. Three question types, and that is the entire
surface:

| Type | Answers | Returns |
|---|---|---|
| `Noul` | Is this statement true? | `noul`, a probability from 0 to 1. No separate confidence. |
| `Choice` | Which of these options? | `choice`, `probabilities` over every option, `confidence` |
| `Score` | Which level on this rubric? | `score` (can land between levels), `legend`, `probabilities`, `confidence` |

Four properties matter more than the API shape:

1. **Every question in a request is evaluated independently and in parallel.** One
   answer never becomes hidden context for another. Adding questions barely changes
   latency and costs only the question's own tokens. Batching 13 questions over a
   54k-character document instead of sending 13 calls was 12.2x cheaper and 10.0x
   faster with *identical* answers.
2. **Answers are constrained to the options you supply.** The model cannot return a
   value outside your set, so code never parses prose. This is why "select, do not
   generate" is the core move: find candidates in code, let Jev pick one.
3. **Confidence is a second decision axis.** The answer says what; confidence says
   whether to act. Low confidence is a usable signal, not a failure.
4. **Judgments become reusable data.** Score once, then re-weight, re-threshold, and
   re-rank in code forever with no further calls.

The design rule the docs repeat hardest: **decompose**. Never ask one broad question.
Ask each independent factor separately and combine the answers with weights you own in
code. When priorities change you edit a coefficient, not a prompt.

## Limits and failure modes

Hard limits (`jev-1.13`, verified on the Models page):

| Limit | Value |
|---|---|
| Price | $0.042 per million input tokens. Output tokens free. |
| Context | 64k per request; 32k for `state` plus the longest question |
| Choice options | 255 maximum, roughly 240 before reliability drops |
| Score levels | 2 minimum, 10 maximum. An 11th returns a server error. |
| Input | Text only. String, JSON object, or array. No image, audio, video. |
| Rate | 250,000 tokens/sec, 1,200 requests/min, adjusted without notice |
| Latency | About 100 to 115 ms per call, measured across two cookbooks |
| Language | English is best. Other languages accepted, lower accuracy. |

Documented failure modes, from the jev-1.13 jaggedness page:

1. **Not a calculator.** Counting, arithmetic, and comparing numeric representations
   are all unreliable. Keep math in code.
2. **Dates are read as text, not ordered quantities.** It cannot reliably tell which
   date is earlier or whether one falls in a window. Extract the parts as Choices over
   enumerated options, assemble and compare in code.
3. **Literal reading.** It answers the question you wrote, not the one you meant. If
   you find yourself explaining what you really meant, that explanation is the missing
   half of the instruction.
4. **Context rot.** Accuracy falls as the state grows with irrelevant content. Filter
   in code first, send only what the question needs.
5. **Not adversarial by default.** State is data, and injected instructions can move
   the answer. Never a security boundary on its own.
6. **No structural invariants.** A Noul and an equivalent yes/no Choice are different
   questions and give different numbers. P(A) and 1 - P(not A) do not have to agree;
   one measured pair summed to 1.19. Never carry a threshold tuned on one primitive
   over to another.
7. **Consistent but not deterministic.** Mean run-to-run probability standard deviation
   is 0.0102, far tighter than any LLM tested, but labels near a threshold still flip:
   2 of 8 questions changed their top label across 15 repeats. The fix is an explicit
   uncertain band (Noul 0.30 to 0.70, Choice top probability under 0.60) routed to a
   person, which took label agreement to 99.2% while still auto-deciding 74.2%.

### PP_Recruiting: not now, and what would change that

Assessed 2026-09-19 against the 009 workbook and the 09-16 validation run. **Nothing
here is worth building today.** Recording it so it does not get re-litigated.

The screening engine itself is out of scope permanently: it compares percentiles to
thresholds (75th percentile, 0.375 elite share, Impact 90+), which is the exact thing
the jaggedness page says Jev is unreliable at. Its real weakness is calibration, not
judgment quality. The 09-16 validation ran low by 0.77 tiers on average, 1.25 against
Power Four, and caught 5 of 15 defensive players. That is fixed by more graded
validation players and code, not by a different model.

Two candidates that looked like fits and are not:

- **Player entity resolution.** Collapses to a code join. Telemetry carries a stable
  `PlayerId`, and `load_leaderboard.py` already joins Player Traits to Advanced Stats
  on it. The one open cross-source question (Jordan Church) is a single name against
  the recap list, and 30 of 30 transfers already matched by hand. One player is not a
  pattern.
- **Role assignment (WR/SLOT, END/JACK, CB/STAR).** The live blocker on deliverable
  010, so this was the one worth wanting. Inputs are alignment codes (OWR/SWR, ILB/OLB,
  OCB/SCB), already deterministic in both scripts, plus percentiles. Nothing
  text-shaped to decide on.

**The one real fit is text to features, and it has no input corpus.** It aims straight
at the weakest spot, defense, where percentile data is thinnest and film language is
richest. But pre-portal FCS and G6 players at week 5 to 6 have Telemetry percentiles
and nothing else. **Trigger: revisit when scouting text exists** — either the personnel
staff member starts writing evals on REVIEW rows (the 30 to 50 names per position he
asked for), or players hit the portal and recruiting services publish on them. Shape
when that day comes: not "is this a good corner," but 20 to 30 independent narrow
questions per note (*Noul: the note describes him redirecting without losing speed.
Noul: the note describes him losing leverage against bigger blockers. Score 1 to 5: how
much of this note is about his hands.*) in one request, weights in our code.

Two constraints that narrow it further whenever it is revisited:

- **Jev cannot live in the workbook.** The staff member runs the weekly refresh himself
  in Excel and Power Query. Any Jev step is Eric-run preprocessing, so it must be
  batch-once like the baseline load, or a standing Monday job. That rules out most of
  what is otherwise tempting, and the weekly refresh is the one piece someone else runs
  without Eric — a network call on that path is a straight downgrade.
- **Tier A here is about the wrong risk.** These are public college players, not Baylor
  athletes, so the health-data tiers do not bind. But Telemetry grades are licensed
  vendor data, and sending 8,761 rows to `api.typesafe.ai` is a question under
  **Telemetry's own terms on third-party processing**. Settle that before any of this,
  including anything small.

## What this unlocks that we cannot do today

Four of these are genuinely new capability, not a cheaper version of something we have.

which is the whole thesis. Our equivalent: coach notes, wellness comments, RTP
narrative, and scouting text become inputs to a model instead of prose nobody scores.
Start on CFB scouting or public text, which is tier A. Athlete narrative is tier B or C
and waits.

## Where not to use it

- **Numeric verification on its own.** Correcting my 09-19 chat answer: the citation
  pipeline does apply to the TOS brief, but the part that catches a misquoted number is
  the **code string-match in step 1**, not Jev. Jev's Choice catches "this section says
  the opposite of the claim" (it flagged one at 0.99 confidence). Use both, and do not
  ask Jev whether 3.2 equals 3.2.
- **Date and window arithmetic.** Kickoff-time math in the sleep scheduler, GPS pull
  windows, availability windows. Extract parts, compute in code.
- **Anything that needs prose out.** It does not generate. Output is free because there
  is none.
- **Any per-athlete GPS, force plate, DEXA, or S2 record**, until Baylor IT says
  otherwise. Our own smoke test already posted a hamstring-tightness note to
  `api.typesafe.ai`. It was synthetic, and it shows how small the slip is.
- **As a security boundary.** The injection Noul is a filter, not a gate. Treat every
  passage that reaches a prompt as untrusted regardless of its score.
