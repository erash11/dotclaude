**Built 2026-08-31.** Closes ARMS gap 5. `~/DEV/CommandCentre/server.py`, served by
`com.keystone.commandcentre` (`RunAtLoad` + `KeepAlive`), own `DESIGN.md`.

**<http://localhost:7373>** — one page answering "is anything broken?": agent
health, backup result, graph progress, logged failures, active projects, and
links to every generated report with its age.

Design rules that must hold, each learned the hard way:

- **Standard library only.** Python 3.14 here is PEP 668-managed, so any
  dependency means a venv to maintain forever. A read-only local page never
  earns that.
- **Rendered fresh per request.** Never cached, never regenerated on a timer. A
  page that can be stale is a page you stop believing — that is exactly why the
  on-demand `project-triage/dashboard.html` never became a front door.
- **A dashboard that contradicts the CLI is worse than no dashboard.** The file
  counter first used `total - len(done)` and disagreed with `gf_remaining.py` by
  13, because the done-list holds entries no longer in the corpus. It now does
  the same **set difference**, and the corpus selection is kept identical across
  `server.py`, `gf_gemini.py` and `gf_remaining.py`.
- **Judge a running service on its PID, not its last exit code.** A `KeepAlive`
  daemon carries the exit code of the instance that *died*, so a restart leaves a
  nonzero code behind permanently. `launchctl list`'s first column is the PID and
  the second is that stale status — reading the wrong column makes a healthy
  service look broken.
- **Live `launchctl` state is the truth**; `run-ledger.json` is shown but never
  allowed to claim a job succeeded. See [[keystoneos-verification-habits]].
- **Every source is optional** — a missing input renders "unknown", never a 500.
- **Bound to `127.0.0.1` only**, which is why it needs no auth. Do not change the
  bind address without adding one. Read-only on purpose: no buttons, so a stray
  browser tab cannot fire an agent. `~/.claude/scripts/skill-button.sh` exists
  for the day buttons are wanted.

**The threat to a localhost service is a web page you visit, not the network.**
Any site your browser opens can make requests to `127.0.0.1`, so binding to
loopback is not a security boundary on its own. **DNS rebinding** is the real
attack: the attacker's domain re-resolves to `127.0.0.1`, their JavaScript
becomes same-origin, and it reads everything. The defence is a **`Host` header
allowlist** — refuse any request whose Host is not a loopback name. Three review
rounds were needed to get the parsing right: compare IPv6 numerically (so
`[0:0:0:0:0:0:0:1]` is recognised), refuse a second `Host` header rather than
guess, strip exactly one trailing DNS dot, and validate the port range. Also
learned: **curl silently collapses duplicate headers** — prove that guard over a
raw socket.

**An allowlisted name is not an allowlisted file.** `Path.exists()` and
`read_bytes()` follow symlinks, so an exact-path allowlist still served
`/etc/hosts` when the target was swapped for a symlink. Confine the resolved
object too, then **read through the same descriptor you checked** (`O_NOFOLLOW`,
then compare the fd's `(st_dev, st_ino)` to the pre-check `lstat`) — checking a
path and reopening it by name is a check/use race. Close the fd in a `finally`
that catches every exception type, not just `OSError`.

**Any number shown in two places must be computed by identical code.** A page
that contradicts the CLI destroys trust in both. Three separate counters here
had to be aligned four times: set difference not arithmetic, the same corpus
selection, the same skip gates, the same `GF_MAXBYTES` env override — including
its "0 means no cap" convention — and the gate applied to a progress line's
numerator *and* denominator.

**Creating any new `~/DEV/<folder>` breaks the backup immediately** — the manifest
is default-deny, so `daily-backup` exits 1 until the folder is added to
`~/.claude/scripts/backup-manifest.json`. Working as designed; just add the entry
in the same turn. The `class` field answers *who keeps this when you leave
Baylor* — `institutional` also copies to Baylor OneDrive ("lost when Baylor
access ends"), `personal` stays yours. See [[backup-sync-system]].

**Current state (2026-09-03).** Two backup runs happen on most days, and the 09-02 entry was
right about that — but **not** because reconcile hard-codes the backup. The real mechanism,
traced 09-03:

`keystone-reconcile.ps1` is a **generic make-up engine**. It has no mention of `daily-backup` at
all; it loops the registry at `DEV/KeystoneOS/data/jobs.json` and calls
`run-job.ps1 -Job <id> -Trigger reconcile -MadeUp` for any job with no success recorded today.
The `daily-backup` job is in that registry with `reconcile: true`, `graceMinutes: 60`,
`maxAttemptsPerDay: 2`, and `makeupWindow: 07:00-20:00`. Its `successProbe` greps today's
`daily-backup.log` for `daily-backup end: OK`. So:

- **If no successful run is recorded by 07:00, reconcile replays it** → the ~07:00-07:10 run.
- **launchd `com.keystone.dailybackup` fires at 09:00 regardless** → the second run.
- **Run the backup by hand before 07:00 and reconcile skips it** ("already succeeded today").
  Confirmed 09-03: a 06:15 manual run logged `OK` at 06:25, and no 07:00 run happened.

Registry inconsistency worth knowing: `jobs.json` records `schedule.at: "00:30"` while the live
plist fires at 09:00. The make-up window is what actually drives the 07:00 replay, so the stale
`at` has not bitten yet. Still true: `launchctl ... runs = 0` proves nothing — read the log.
Receipts cluster only on days CRASHBOX is attached: a mount gap, not a schedule gap.

**"Scheduled runs cannot push" is NOT yet established — and the two contexts differ.** On
2026-09-03 the **09:00 launchd** run pushed `global-memory` cleanly and ended `OK (0 errors)`:
no `PUSH FAILED`, no `PUSH ERR`. But the **reconcile/`run-job.ps1`** context — which is where the
09-02 07:08 and 08-13 07:00 failures happened — **was not exercised that day**, because the manual
06:15 run pre-empted the replay. Do not read 09-03 as clearing the gap; it only clears launchd.
`daily-backup.ps1:74` no longer swallows the reason: the `Out-Null` was replaced 09-03 with
captured output that logs `REPO <name> : PUSH ERR | <text>` on failure only. **The error text will
only appear on a day nobody runs the backup by hand before 07:00.** Diagnose from that line rather
than assuming a credential gap. `daily-backup.err` is stale (last written 2026-08-06); never read
it as current. Manual remedy after a failed push is still `git -C <repo> push origin main` for
SecondBrain, `.claude/global-memory`, `.claude`.

**SSD layout:** non-repo DEV dirs land in `DEV-nonrepo/`, **not** `DEV/` — there is no `DEV/`
on CRASHBOX (roots are `DEV-nonrepo/`, `DEV-repo-data/`, `DEV-working-tree/`, `claude/`,
`codex/`, `gemini/`, `SecondBrain/`, `_receipts/`). `._`-prefixed files beside every real file

The nightly backup is `~/.claude/scripts/daily-backup.ps1` (pwsh, launchd

## Traps that cost time

- **Milvus is NOT in the memsearch path**, despite what `RESTORE.md` and the Bucket docs
  say. Indexing works with port 19530 closed and Docker not installed. Don't set it up.
- **`-DryRun` cannot verify a write path.** It passes `rsync -n`, which writes nothing. A
  snapshot that fails live will show `OK` in a dry run. Only a non-dry run is evidence.
- **Never size up a DriveFS destination with `du`.** It reports local cache/allocated
  blocks, not logical size — the `codex/sessions` mirror read as "47 MB of 289 MB" while
  actually holding 255 of 256 files, with a 35 MB file verified byte-identical by
  `stat -f%z` on both sides. Compare **file counts and per-file byte sizes**, never `du -sh`.
- **`snapshot:sessions` is a genuine hang** — not a size problem, not a lock, not a
  permission fault, and not slow enumeration. Three wrong theories died here in one
  session; see the evidence section below before forming a fourth. **Bounded 2026-08-14**
  by a watchdog in `Invoke-Rsync` (900s ceiling, hard SIGKILL, records `rsync-timeout`),
  committed as `8863a37`. That caps the symptom so the run reaches the SSD capture. The
  wedge itself is still unexplained.
- **Tier A memory is NOT in git.** `~/.claude/.gitignore` line 1 is `/*` (default-deny
  allowlist) and `projects/` is not allowlisted, so `projects/*/memory/*.md` has exactly
  two backup layers: the Drive SNAP of `~/.claude/projects`, and the SSD. With CRASHBOX
  unmounted that is a single copy. Nothing to "commit" there — it's by design.
- **`daily-backup.ps1` refuses to merge diverged repos by design** — that's correct
  behavior, not a bug. Reconcile by hand.
- **stack-doctor's cloud heartbeat** watches the newest per-run receipt
  (`_receipts/run-*.txt`). It used to watch `RESTORE.md`, which the job *copies*
  (`Copy-Item -Force`, line 411) rather than rewrites, so its mtime never advanced and the
  check cried `backup-cloud-stale (218h)` while DriveFS was healthy. Fixed 2026-08-14.
- **Untracked files block a fast-forward**, and plain `git stash` does not pick them up —
  needs `-u`, or rename them aside. Bit the documented SecondBrain fix.
- Reading exit codes through a pipe returns the *last* pipeline element's status, not the
  command's — see [[zsh-shell-traps]]. This produced two wrong readings in one
  session (`rsync ... | tail` and a stack-check run).

## `snapshot:sessions` — evidence from a live reproduction, 2026-08-14 15:20 (stack-doctor)

Caught the hang in progress and narrowed it. **Root cause still open** — this section is
evidence, not a verdict. Everything below is measured, not inferred:

- **It is a hang, not a slow transfer.** Four rsync processes (client `-a ... codex/sessions/`,
  its `--server` receiver, plus two older receivers) sat at **0.01–0.03 s of CPU across
  34–85 minutes** of wall clock. Zero progress, not slow progress.
- **Nothing is left to copy.** The mirror is **256/256 files** — the previously-missing
  `2026/08/06/rollout-*.jsonl` is present. A complete mirror still hangs.
- **The mount is healthy.** A recursive `find` over the destination returned 256 files
  promptly, and `touch` inside the exact hung directory succeeded instantly. Reads *and*
  writes both work, so this is not a wedged DriveFS/FUSE mount.
- **The wedged processes ignore SIGTERM** (still alive minutes later in `S` state) — they
  are blocked inside a call that neither returns nor delivers signals.
- **Dry runs cannot see it**: `-n` completes clean, live runs hang. Another instance of the
  "`-DryRun` cannot verify a write path" trap above.

### Orphans are a symptom, not the cause

Two `rsync --server` receivers were **orphaned to PPID 1** (started 13:55 and 14:33). It is
tempting to call them the blocker; the timeline refutes it — the **10:31:54 run hung at the
identical point** (last line `SNAP skip (missing): .codex/memories`, no end line) while the
oldest surviving orphan did not exist until 13:55. `kill` on both orphans did not unblock
the live pair either.

Why they accumulate: **`daily-backup.ps1` contains no `pkill` at all** (verified by grep —
do not go looking for one). The anchored `pkill -f "^/usr/bin/rsync"` belongs to an *ad-hoc
wrapper used interactively in another session*. That pattern matches only the client, whose
`argv[0]` is the full path; the `--server` child's `argv[0]` is bare `rsync`, so
`pgrep -f "^/usr/bin/rsync"` returns the client alone. Every kill-and-retry therefore strands
one more receiver. If that wrapper is reused, match on `-x rsync` or the destination path.

### ROOT CAUSE FOUND 2026-08-14 17:00 — it is not rsync

Ran the copy in the foreground with `-avv`, unpiped. It printed ~99 lines of
`... is uptodate` and froze mid-filename. Then:

- `sample <receiver-pid>` showed the process blocked in **`__mmap`** — one frame, not moving.
- `lsof` on it showed FD 5 open on a specific **destination** file:
  `codex/sessions/2026/05/08/rollout-2026-05-08T17-14-58-019e09a8-*.jsonl`.
- **`head -c 512` on that destination file hangs by itself**, with zero rsync processes
  running. A plain read. So the file is unreadable through DriveFS.
- A 44-file sample elsewhere in the same mirror read instantly, so it is **specific files,
  not the mount**.

The files are **DriveFS placeholders** — uploaded to Google, then evicted from the local
cache. Census of the destination on 2026-08-14: 256 files, **122 materialized (48.5 MB on
disk), 134 placeholder-only (240.7 MB logical, 0 bytes local)**. Source is 256/256
materialized. Detect with `stat -f '%b %z'`: blocks==0 with a nonzero logical size means
the content is not local. Reading one forces an on-demand fetch, and that fetch stalls —
which is what blocks `__mmap`. rsync was the victim, not the cause. **Do not chase rsync
flags**; the block happens at open, before any comparison strategy applies.

**This inverts the problem: the backup is fine, the verification is what's broken.** All
256 files are on Google's servers. Nothing is missing. What fails is the *next* run's
attempt to re-read them to confirm they match. Never conclude "the snapshot is broken"
from this failure mode.

Also: `du -sh` on the destination reports the *local cache* (48 MB), not the logical 289 MB.
Both numbers are true and mean different things — do not treat the gap as missing data.

Diagnostic sequence that worked, reuse it: `sample <pid>` for the blocking syscall →
`lsof -p <pid>` for the file it is on → bounded `head -c` on that path to prove the
filesystem, not the tool, is at fault.

**Attempted fix that DID NOT WORK**: pinning `My Drive/Backups` "Available offline" via the
Finder context menu (there is no CLI or xattr for it — the app ships no control surface).
Eric pinned it 2026-08-14 17:30. Result: **one** file materialized, then flat for 5 minutes
(133 placeholders, 49.2 MB, unchanged). Restarting Drive did not help either.

**DriveFS on this Mac is itself unhealthy** — this is the real blocker, not rsync and not
the pin:
- It refused a graceful `osascript quit` for 20s and needed SIGKILL. Its log emitted
  `crashpad ... ThreadsStuck` every 6s. Restarting cleared the stuck threads but nothing else.
- The **download** queue fails, not just uploads: `merger.cc:969:ProcessDownloadEvent` +
  `HandleFailedChange [DownloadMergeQueueItem]`. DriveFS cannot pull content *down*.
- Signs of local DB damage: `item_query_handler.cc:1135:OnGetItemIds Ignoring item
  local-376561 that's missing from ...`.
- NOT quota: 671 GB used of 5.5 TB.

**Do not clear the DriveFS content cache as the remedy.** It converts every materialized
file into a placeholder needing re-download, feeding the exact mechanism that is failing —
122 readable files could become 0. If DriveFS is repaired, do it by signing out and back in
to force a DB rebuild, deliberately, with time to watch it.

### RESOLVED 2026-08-14 — the backup was never broken, the verification was

**Final mechanism**: files Drive has evicted from local cache are placeholders. Fetching a
placeholder through DriveFS is *unreliable* — usually fast, sometimes stalling for tens of
minutes. rsync blocking on such a fetch is the entire "wedge". Proof it is a slow fetch and
not a poisoned file: the file that hung four separate times **now reads instantly**, and its
blocks went 0 → 770,048 — the repeated read attempts eventually completed the fetch. Six
other placeholders read fine first try. Nothing was corrupt.

**`~/.claude/scripts/verify-drive-backup.sh` (`0d2edb5`) is now the way to verify.** It
compares the Drive API's server-side `md5Checksum` against a local md5 — metadata only, no
DriveFS read, batched ~25 names per query. First run on `~/.codex/sessions`:
**256/256 verified, 0 mismatch, 0 missing.** The snapshot that logged `FAILED` for days was
complete and byte-correct the whole time.

Do not "fix" this by deleting Drive copies. Both files that hung were verified byte-identical
to source *before* anything was touched — deleting would have destroyed a good backup to
repair a read path.

**It is plain fetch latency, scaling with file size** — no mystery left. A full read-scan of
all 256 files with a 6s per-file cap: 33 stalled, and those averaged **2,301 KB vs 1,156 KB
for the set overall** (max 15.8 MB). Bigger file, longer fetch. Nothing file-specific,
nothing corrupt. The scan itself moved the mirror from 122 → 230 materialized (48.5 → 161.8 MB
local), which is exactly what "reading materializes it" predicts.

Caution when testing this: **reading a file materializes it**, so any scan warms the cache and
a later run passes for reasons that will not hold once Drive evicts again. Timestamp results
and never treat a post-scan rsync run as a clean verification.

### Why DriveFS is unhealthy — found 2026-08-14 18:20

**Google Drive is mirroring `~/DEV` as a device-backup folder named "My Mac"**, including
**34 `.git` directories / 3,470 files**. VS Code has `"git.autofetch": true`, which rewrites
every repo's `FETCH_HEAD` on a 180s cycle; Drive uploads all 34 each time. That is the source
of the `PRECONDITION_FAILED` storms on `FETCH_HEAD` and the stuck threads in `drive_fs.txt`,
and therefore of the slow placeholder fetches upstream.

Proof (not inference): local `~/DEV/*/.git/FETCH_HEAD` all stamped 18:22:09 while Drive's
server copies read `2026-08-14T23:22:09Z` — same second — and the Drive parent chain resolves
`FETCH_HEAD → .git → DataBase_GPS_Reporting → DEV → My Mac`.

**`OneDrive-Import` was a red herring** — it holds 22 `.git` dirs / 7,292 files, but they are
static archives and do not churn. Don't chase it.

**FIXED 2026-08-14 ~18:28 — Eric removed `~/DEV` from Drive Preferences → "Folders from your
computer" (keeping the cloud copy). Verified, and it worked:**
- Server-side `FETCH_HEAD` froze at `23:28:12Z` while local `~/DEV` copies kept updating
  (18:32:28) — churn decoupled, `git.autofetch` left ON as intended.
- `PRECONDITION_FAILED` 14 → **0**. `ProcessDownloadEvent` errors 11 → **0**.
  `HandleFailedChange` stable (idle retry backlog, not growing).
- Google Drive CPU **64.6% → 0.0%**.
- **End-to-end: 5/5 genuine placeholders (blocks==0) fetched in 2–3s each**, where the same
  class of read previously stalled for minutes or indefinitely. This is the actual cure for
  the `snapshot:sessions` wedge — the watchdog only bounded it.

Original recommendation, for the record: remove `~/DEV` from Drive Preferences → "Folders
from your computer", choosing KEEP for the existing cloud copy. The mirror is redundant and
strictly worse than the nightly, which already covers `~/DEV` via 68 manifest entries →
SSD + GitHub with `.git` excluded and credential files denied (6 projects hit that policy on
2026-08-14). **Do not** "fix" this by disabling `git.autofetch`: that masks the symptom, costs
a useful feature, and leaves 3,470 `.git` files still mirrored to churn on every commit and
checkout. Verify afterward by re-querying `FETCH_HEAD` modifiedTime via the Drive API and
re-checking `drive_fs.txt` for `ThreadsStuck` / `PRECONDITION_FAILED`.

How to check whether anything is pending before any Drive surgery: sample
`grep -c HandleModifiedLocalItem/HandleFailedChange/DownloadMergeQueueItem` in
`~/Library/Application Support/Google/DriveFS/Logs/drive_fs.txt` over ~90s — flat counters
mean idle queues. **Do not** use the presence of `com.google.drivefs.item-id` as an
upload-pending signal: 774 files in Backups lacked it and were all already on the server.

Rejected: `--ignore-existing` (would freeze any mid-session rollout file at its partial
size in Drive permanently) and leaving the watchdog to absorb it (~15 min wasted nightly,
and two standing errors would camouflage real ones).

Note `-W` (whole-file) is already default for local transfers, so `--whole-file`,
`--size-only` and delta-algorithm tuning are all dead ends here — the block happens on
open, before any comparison strategy matters.

## The SSD layer's real failure mode — schedule/mount mismatch, found 2026-08-29

**The nightly is healthy; the SSD layer is simply absent at run time.** `com.keystone.dailybackup`
fires at 00:30 and CRASHBOX is normally unplugged then, so every run logs
`TARGET SSD /Volumes/CRASHBOX/AssistantBackup NOT MOUNTED - orphan and working-tree capture
SKIPPED this run` and ends `OK (0 errors)`. A clean exit code is therefore **not** evidence the
SSD captured — the skip is not an error. Check `_receipts/run-*.txt` mtime on the drive instead.

Receipt history proves the pattern: 10 SSD captures total, clustered on days the drive happened
to be attached (Aug 6, Aug 14 ×5, Aug 15, Aug 16, Aug 17), then a **12-day gap** to Aug 29. Eric
read this as "the SSD backup has never run"; it had, just rarely.

**Manual run is the remedy and takes ~6 minutes**, not the ~45 the 2026-08-14 notes imply:
`/opt/homebrew/bin/pwsh -File ~/.claude/scripts/daily-backup.ps1` (no SSD-only switch exists; do
not add one). Run 20260829-073713: Drive SNAPs finished in **6 seconds** — the `codex/sessions`
wedge is genuinely gone since the `~/DEV` de-mirroring fix — DEV capture 07:37–07:40, `.claude`/
`.codex`/`.gemini`/SecondBrain state 07:41–07:42, `RECEIPT ssd : verified` at 07:42:50,
`end: OK (0 errors)` at 07:43:14. SSD 25 → 27 GB. The long tail in the 00:34 nightly was the
memsearch INDEX step (00:51→01:18), which runs *after* the backup and is not part of it.

Verification trap repeated here: **top-level SSD directory mtimes stay old after a successful
capture** (`SecondBrain` still read Aug 17, `claude` Aug 14) because `rsync -a` preserves source
mtimes and a parent dir's mtime only moves when an entry is added or removed at that level. The
`STATE-SSD ... : OK` log lines and the receipt are the evidence; mtimes are not. See also
[[keystoneos-verification-habits]].

**RESOLVED 2026-08-29**: schedule moved 00:30 -> 09:00 in
`~/Library/LaunchAgents/com.keystone.dailybackup.plist` (PlistBuddy `Set :StartCalendarInterval:Hour 9`,
then `launchctl bootout gui/$(id -u)/com.keystone.dailybackup` + `bootstrap`; live schedule confirmed
`Hour => 9, Minute => 0` via `launchctl print`). Old plist kept at `.plist.bak-2026-08-29`. 09:00 was
chosen from mount evidence (drive attached 07:31 on 08-29; the 08-17 capture ran 08:05). **Do not
verify this by mtime or by exit code** — the only proof is a fresh `_receipts/run-*.txt` on the drive
dated 08-30 or later. If receipts still cluster, the drive is not attached at 09:00 and the hour is wrong.

`~/.claude/global-memory/transcripts/.errors.log` archived to `.errors.log.archived-2026-08-29` and
cleared the same day. It held two **still-open** issues, not stale history: memsearch `onnxruntime`
import failure (2026-08-22, corroborated by `INDEX full set: Indexed 0 chunks` on 08-28/08-29), and
stack-doctor weekly flagging `errors-log`, `flush-stale`, `memfile-full:MEMORY.md` (2026-08-24).

**Both cleared by end of 2026-08-29** — stack-doctor returned `ALL CLEAR`: memsearch `search: OK`,

## A stalled run with no rsync child = an unanswered macOS access prompt (2026-09-03)

`daily-backup.ps1` gates both optional destinations on a bare `Test-Path` with **no timeout**:
`Test-Path $GDrive` (section 2a) and `Test-Path $SsdRoot` (section 2b). When macOS has a pending
TCC/removable-volume permission prompt for that path, the call blocks **forever** — and because 2a
runs before 2b, the SSD capture never happens and no receipt is written.

**The tell:** `pwsh` alive in `S`/`SN` state, **zero rsync children**, and the log frozen mid-run.
That is not a slow copy — a slow copy always shows an `rsync` process. `ps -axo pid,stat,comm` on
macOS marks I/O wait `U`, not `D`; a `D`-state grep finds nothing and proves nothing.

**The fix is the human, not the shell — look at the screen for a pending prompt FIRST.** On
2026-09-03 both `~/Library/CloudStorage/GoogleDrive-*` and `/Volumes/CRASHBOX` were unresponsive to
a plain `ls`. The Drive half cleared after a quit/relaunch of Google Drive, **but Eric was
approving access prompts in that same window — the relaunch is unproven and may have done nothing.**
Do not treat killing Google Drive as the known fix. The SSD half cleared only when he approved the
prompt. **Do not force-unmount CRASHBOX** (exFAT, no journal) — ask first.

Probably (unverified): the Claude Code shell and the launchd/reconcile jobs are different TCC
principals, so this prompt should not recur for the scheduled runs — but it may fire once per new
app that launches the script.

**Never re-run without `pkill -f daily-backup.ps1` first.** A hung run is harmless, but several hung
runs unblock *together* the moment access is granted and race onto the SSD — the two-writer
corruption this whole system exists to prevent.

**Timing that matters:** reconcile replays the backup at 07:00 if no `OK` is logged for today, and
launchd fires at 09:00 regardless (see "Current state" above). A manual run finishing before 07:00
suppresses the replay; one finishing after 07:00 can collide with it.

Open gap, not yet fixed: neither `Test-Path` has a watchdog, unlike `Invoke-Rsync`
(`$RsyncTimeoutSec = 900`). Worth wrapping both.
