# /project — portfolio registry skill

Drives the `project-triage` CLI to capture ideas, log progress and change
project status. The registry (`portfolio.json`) is the single source of truth.
The live board (`board.py`) is its front door and re-renders on its own within
a few seconds of any registry change, so there is nothing to render or publish.
(The static `dashboard.html`, its Artifact and `pulse.md` retired 2026-10-03.)

## Paths

- Config: `~/.claude/skills/_shared/config.windows.json` on Windows; `config.macos.json` on macOS
- Repo: parent directory of `portfolio_json` in the selected platform config
- Interpreter: `python` on Windows; `python3` on macOS
- Registry: `portfolio_json` in the selected platform config
- CLI entry points: `portfolio.py` (mutations and checks), `board.py` (the board)

## CLI contract (verbatim — do not alter flags)

```
python "<project-triage-repo>/portfolio.py" add-idea "<pitch>" --source "<source>"
python "<project-triage-repo>/portfolio.py" add-update "<name>" "<note>" --next-action "<optional>"
python "<project-triage-repo>/portfolio.py" set-stage "<name>" "<stage>"
python "<project-triage-repo>/portfolio.py" set-status "<name>" active|paused|done --note "<optional>"
python "<project-triage-repo>/portfolio.py" set-receiver "<name>" "<who, or me: why>"
python "<project-triage-repo>/portfolio.py" slate-check
python "<project-triage-repo>/board.py" --background
```

- `add-idea` prints `idea captured (<N> in inbox)`.
- `add-update` prints `updated <name>` (name match is case-insensitive).
- `set-stage` prints `stage set: <name> → <stage>`. Valid stages, in ladder
  order: `idea grilled spec planned building shipped`.
- `set-status` prints `status set: <name> → <status>`. It is the board's
  Start/Park/Done: a start over the slate cap is refused, and a start begins
  the 7-day clock.
- `slate-check` loads (and so validates) the registry and prints the slate
  rules; exit 0 means a hand-edit is structurally valid.
- `board.py --background` reuses the running board or starts one, opens it,
  and prints its URL.
- Any error path prints `[error] <msg>` to stderr and exits 2, with no
  mutation to `portfolio.json`. Stop and surface the message verbatim.

## Verbs

### `idea <pitch>`
Run `add-idea "<pitch>" --source "<conversation context, ≤8 words>"`. The
source should summarize where the idea came from (e.g. "chat about GPS
vendor gaps"), not just "chat".

### `update <name> <note>`
Fuzzy-match `<name>` against the project names currently in the registry
(read `portfolio.json` first). If exactly one match, run `add-update "<name>"
"<note>"` (add `--next-action "<...>"` if the user gave one). If the match is
ambiguous or there's no close match, ask the user which project they mean
before running anything.

### `start` / `park` / `done <name>`
Fuzzy-match like `update`, then `set-status "<name>" active|paused|done`.
A start on a job/side/tool project needs a receiver within 7 days: if it has
none, ask who it is for and run `set-receiver` (never invent one).

### `rank`
Read `portfolio.json`, show the lane's active projects with their current
`rank` values, and ask for the new order. Never reorder ranks yourself —
only apply the order the user gives you. Rewrite the `rank` fields directly
with the Edit tool, then validate with `slate-check` (exit 0 = valid).
Dragging on the board does the same thing and is usually quicker.

### `promote <idea>`
Ask which lane (`job`, `side`, `system`, `knowledge`, `tool`) and for a
`next_action`. With the Edit tool: set the matching idea's `status` to
`promoted`, and append a new project entry to that lane at the next free
`rank` (max existing rank in that lane + 1). Validate with `slate-check`.

### `stage <name> <stage>`
Fuzzy-match `<name>` like `update` does. Run `set-stage "<name>" "<stage>"`.

**Shipped → harvest handoff:** when the stage being set is `shipped`, offer
once: "Want me to run /harvest on <name> to distill it into your SecondBrain
and log the shipped artifact?" On yes, invoke the `harvest` skill for that
project.

### bare `/project`
Run `board.py --background` and give the URL, then show `slate-check` output
in chat.

## After every mutation

Nothing to render: the board picks the change up on its next poll. Say what
changed in one line. Registry edits are committed by closeout as
`data: board edits <date>`; do not commit them mid-session unless asked.

## Rules

- Never reorder project ranks yourself — only apply the order the user
  gives you during `rank`.
- Never delete a project or idea without explicit confirmation.
- On any `[error] ...` output from the CLI: stop immediately and show the
  error verbatim.
- `portfolio.json` is the single source of truth; tasks live in each repo's
  `docs/STATUS.md`, which the board reads and never writes.

# Project Triage

The user's daily project-portfolio dashboard. Renders an HTML view of every top-level folder in `~/DEV/` with status pills (resume / pause / done / kill / archive), heuristic activity metrics, and curated purpose/action prose.

## Vault & files

- **Skill dir:** `~/.claude/skills/project-triage/`
- **Script:** `triage.py` (Python 3.11+, no deps beyond stdlib)
- **Scan root:** `~/Desktop/DEV/` on Windows; `~/DEV/` on macOS
- **Output dir:** `<scan-root>/project-triage/`
- **Output file:** `YYYY-MM-DD.html` (one per day)
- **Curation file:** `<scan-root>/project-triage/.curation.json`
- **Python:** `python` on Windows; `python3` on macOS

## Flow

### 1. Check whether today's already been generated

Glob `DEV/project-triage/*.html`. If today's date file exists, ask:
> Today's triage already exists. Regenerate, or open the existing file?

If "open existing," just `start` it in the browser and exit.

### 2. Check for a missed yesterday

If today's file doesn't exist *and* yesterday's also doesn't exist, this is the morning-after case. Offer:
> Yesterday's triage was never generated. Want me to backfill it first, then run today's? (recommended)

If yes, run with `--date <yesterday>` first, then today's.

### 3. Generate the report

```bash
python "$HOME/.claude/skills/project-triage/triage.py" --open
```

Pass `--date YYYY-MM-DD` for a backfill. The `--open` flag launches the default browser when generation succeeds.

### 4. Read the drift output

The script prints a `drift:` line listing projects whose curated state needs attention. Three drift signals:
- **Heuristic mismatch:** curated status disagrees with what the activity heuristics now say (e.g., curated "resume" but no files touched in 45d)
- **Stale curation:** the `curated_at` timestamp on the entry is > 30 days old
- **Active-but-uncurated:** a `resume`-classified project has no curated `purpose` (you haven't told the user what it does yet)

If `drift: 0`, the report stands on its own. Report:
> Today's triage at `DEV/project-triage/<date>.html` · N projects · no drift.

If drift > 0, ALWAYS offer the curation pass — never silently update entries:
> N projects show drift. Want to walk through them now, or revisit later? (the ⚠ flags will stay in the dashboard until you do)

### 5. Curation pass (only if user opted in)

For each drifting project, use `AskUserQuestion` to surface ONE focused decision per project. Possible question shapes by drift type:

**Heuristic mismatch** (curated says X, heuristic says Y):
> `<project>` is curated as `<curated>` but heuristics now classify it as `<heuristic>`. What's the right call?
> - Keep curated status (override stays)
> - Adopt new heuristic status
> - New status: [other option]

**Stale curation** (>30d old, no heuristic disagreement):
> `<project>` was last curated `N` days ago. Quick re-confirmation:
> - Still accurate, refresh timestamp
> - Update purpose/action
> - Remove curation (let heuristics drive)

**Active-but-uncurated** (resume, no purpose):
> `<project>` is active but has no curated purpose. Want to add one?
> - Yes, I'll dictate purpose + action
> - Skip — leave heuristic-only
> - Mark for later (do nothing this run)

If the user wants to dictate prose, take their reply verbatim, update `.curation.json`, and stamp `curated_at` to now.

**Curation file schema:**
```json
{
  "<project-folder-name>": {
    "purpose": "string — what this project is and what it's for",
    "action": "string — next step or context for whether to touch it",
    "status_override": "resume|pause|done|kill|archive",
    "curated_at": "ISO-8601 datetime"
  }
}
```

Only the fields you're setting need to be present per entry. `status_override` is optional — when absent, heuristics drive the status.

After updates, re-run the script (without `--open`) so the saved HTML reflects the new curation:
```bash
python "$HOME/.claude/skills/project-triage/triage.py"
```

### 6. Sign off

Three lines max:
- File: `DEV/project-triage/<date>.html`
- Status counts: N resume, N pause, N done, N archive/kill
- Drift handled: N updated, N deferred (with the project names)

## What NOT to do

- **Don't auto-update `.curation.json` without explicit user approval per entry.** This file is sacred — it's the user's working judgment about their own work.
- **Don't run the script on directories outside `~/DEV/`.** The whole point is that it's the DEV portfolio surface.
- **Don't generate prose for the user.** The user said heuristics-only + later evolves toward curation. When they're ready to add purpose/action, they tell you what to write. You don't infer it.
- **Don't reclassify a project as "kill" or "archive" without confirming.** Heuristic kill/archive in the dashboard is fine (it's just a recommendation), but if you're updating the curation file to override status, ask first.
- **Don't run more than once per day** unless the user explicitly asks to regenerate (e.g., after a curation pass, which is intentional).

## Edge cases

- **Backfill request for a date older than yesterday:** allow it (`--date YYYY-MM-DD`), but flag: *"Note: the script reads current file mtimes, not historical state. A backfill labels the report with that date but the metrics are from right now."*
- **Empty `DEV/`:** rare, but the script handles it cleanly (renders an empty dashboard). Tell the user there's nothing to triage.
- **Python missing or path differs:** fall back to `python3` then `python`. If all fail, surface the error verbatim and stop.
- **A project whose every file sits on a bulk date:** the script falls back to the raw newest mtime so it still dates and sorts, rather than dropping out of the report. Its date will read as the bulk date — treat that as "unknown", not as work.

## Gotchas

- **`.DS_Store` files silently fake activity.** Finder stamps one into every folder it displays, so merely browsing `~/DEV` in a window makes dormant projects look touched today. The script skips `JUNK_FILENAMES` (`.DS_Store`, `Thumbs.db`, `desktop.ini`, `.localized`) everywhere it reads mtimes. On 2026-08-09 this alone made 19 projects read as active off 21 files.
- **A restore or migration resets mtimes across the whole portfolio.** `detect_bulk_dates` treats any date appearing in ≥15% of projects (floor of 8) as machine-made and excludes it from activity. Breadth is the signal, not volume — real work spans a few projects a day, a restore spans twenty. Excluded dates are printed as `[info] bulk dates excluded`; if that line names a date you actually worked, raise the threshold rather than deleting the check.
- **Heuristics measure recency; curation measures intent.** A project you consider active but haven't opened in a month will always show as a mismatch. That flag is information, not an error — do not "resolve" it by overwriting the user's judgment.
- **`~/DEV/project-triage/` is a separate repo** that carries its own similarly-named scripts and a scheduled `dashboard.html`. Changes to this skill do not touch it.

# Forecast Capture

Freezes cfbvictorymodel.com's forecasts for the coming weekend, then reports
what changed. Takes no arguments and asks nothing — all 16 Big 12 teams and
2026 are the defaults and rarely change.

## Why this exists

The report's "Chance of Victory" column is **overwritten with the realised
result** once a game is played. Across 2019–2025 that destroyed every pre-game
probability the model ever produced. Miss a week and that week's forecast is
gone permanently — it cannot be recovered later. This makes 2026 the first
gradable season.

## Run it

One command does everything — capture all 16 Big 12 teams, compare, and copy
both into the archive:

```bash
/Users/kristinarash/DEV/CFB_Victory_Model/scripts/weekly_run.sh
```

That wrapper is the only route to run. It hardcodes the absolute `uv` path
(`/Users/kristinarash/.local/bin/uv`) so it works from any shell, and it calls:

```bash
uv run --with playwright python weekly_capture.py            # default = all Big 12
uv run python compare_snapshots.py --all --archive
```

Pass through to narrow it — `scripts/weekly_run.sh --team Baylor` for one team,
`--year 2027` for another season.

Snapshots are written to `data/weekly_snapshots/` (canonical) and copied to
`~/DEV/CFB_Forecast_Archive/<season>/` together with each team's comparison
text. The archive is a read-only mirror; never treat it as the source.

Then read the comparison output back to the user in plain language (see below).

**Budget ~10 minutes.** Sixteen teams share one report session. This is a
hobby server run by one person — do not run it more often than weekly, and do
not add teams beyond the conference without a reason.

**Must run headed.** A Chrome window will open — that is expected, not a bug.
In headless mode Power BI's virtualised slicer list never renders past the
first ~8 alphabetical teams and most teams are unreachable. Do not add
`--headless`.

`Team attempt 1 failed, retrying...` in the output is **normal** — the first
slicer interaction races the app's own start-up. It retries 3×, and any team
still failing gets one whole extra pass at the end. Only treat it as a failure
if a team appears in the final `FAILED for:` line.

## What to report back

Lead with how many of the 16 teams captured, then give the rollup table
`compare_snapshots.py --all` prints (team, expected wins, change, played,
moved). Then:

1. **Games played since last capture** — the forecast is now gradable for
   those. Report side correct/wrong and margin miss. This is the accumulating
   track record; it is the whole point.
2. **Forecasts that moved** — which games and by how much. A big win-probability
   swing usually means the model re-rated an opponent after their weekend.
3. **Season outlook drift** — expected wins now vs last week.
4. **Anything anomalous** — a new game appearing, a game vanishing, fewer than
   12 rows, or a wild swing worth a second look.

Keep it short. If nothing moved, say so in one line.

## Timing

Run **Wednesday** of a game week. Wednesday sits after the model has ingested
the previous weekend and safely before Thursday-night kickoffs. Monday risks
catching the model mid-update; Friday risks missing a Thursday game.

If the comparison output warns the newest capture is several days old, tell the
user which week was missed — that forecast is unrecoverable and the gap should
be recorded rather than quietly ignored.

## Which machine

**The Mac owns the weekly capture (decided 2026-09-23).** On Windows, do not run
it — stop and tell the user. On 9/23 both machines captured Baylor, and the sync
merge conflicted on `data/weekly_forecast_log.csv` and that day's snapshot.

## Which teams

The default is the whole Big 12 — all 16, every week. The list lives in one
place, `BIG12` in `weekly_capture.py`. Edit that constant if the conference
changes; do not scatter team lists into the wrapper or this file.

Outside the Big 12, only if asked. Each extra team is another slow slicer set
against one person's hobby server:

```bash
scripts/weekly_run.sh --teams Baylor TCU "Texas Tech"
```

Team names must match the report's Team slicer exactly — "Iowa State", not
"Iowa St."; "UCF", not "Central Florida". A wrong name fails loudly with
`never appeared (saw [...])` and that message lists what the slicer really
offers, so read it rather than guessing again.

## Gotchas

- **`playwright` is not installed on any Python on this machine.** `weekly_capture.py`
  imports it, so the bare `python3 weekly_capture.py` form this skill documented until
  2026-09-02 dies with `ModuleNotFoundError` before opening a browser. `uv run --with
  playwright` fetches it per-run (~12ms, cached). Never remove `--with playwright` from
  the run block. `compare_snapshots.py` is stdlib-only and does not need it.
- **The browser cache is separate from the Python package.** A `ModuleNotFoundError` is
  never a reason to re-download browsers. But `uv run --with playwright` pulls the newest
  playwright, and each release wants its own build under `~/Library/Caches/ms-playwright/`.
  On 2026-09-23 it jumped from `chromium-1234` to `chromium-1243` and the capture died
  with `Executable doesn't exist at .../chromium-1243/...`. Fix, then re-run:
  `uv run --with playwright python -m playwright install chromium` (~95 MB).
- **Check what already exists before capturing.** `ls data/weekly_snapshots/` first. On
  2026-09-02 the newest file was `2026-07-31_baylor.csv` — pre-season. Report a gap like
  that explicitly instead of just capturing today and reporting success. **But check the
  schedule before calling it a loss.** An old newest-file does not prove a missed week: on
  2026-09-02 Baylor's opener was still 5 days away (2026-09-05), so no forecast had been
  overwritten. A week is only lost if a game was actually played inside the gap. Confirm
  with the ESPN schedule API (Baylor team id 239):
  `curl -s "https://site.api.espn.com/apis/site/v2/sports/football/college-football/teams/239/schedule?season=2026"`
  and check each event's `status.type.name`.
- **This skill cannot run unattended.** The headed-Chrome requirement means
  `skill-button.sh forecast-capture` still opens a window and needs a logged-in session.
  It is not safe to wire to launchd as a silent job.

# Session Miner

Pull uncaptured learnings out of recent session history. Data-gathering skill: it reads history and proposes destinations; the user picks.

## Step 0 — read the pending ledger first

`~/.claude/claude-memory-compiler/reports/proposals-pending.md`

Do this **before** mining. Apply anything marked `approved` (then mark it `applied`), and
re-list every `open` item alongside this run's findings. Append new findings as `open`,
deduplicating against what is already listed. Without it, a proposal made in a session
that ends is lost and the next run pays to rediscover it.

## Sources, in order

1. `~/.claude/global-memory/transcripts/*.md` (last 7 days)
2. `~/.claude/claude-memory-compiler/daily/*.md` (last 7 days)
3. **Raw session records** — `~/.claude/projects/<slug>/*.jsonl`. See below.
4. `memsearch search "<topic>" --top-k 5` for targeted digs

Sources 1 and 2 are already-filtered summaries: a flush decided what mattered before
you ever saw it. Anything the filter dropped is only in source 3. Reach for it when a
run of sources 1–2 comes back thin, or when the user asks about something older than
the 7-day window.

For anything beyond a quick scan, spawn a subagent to do the trawling and return only findings — raw transcript text should not fill the main conversation.

## Mining the raw `.jsonl` records

Several hundred files and a few hundred MB sit in `~/.claude/projects/` (424 files,
337 MB on 2026-09-02, and growing). Feeding that to an LLM is how the compiler's
9.5M-token incident happened, so this source is **capped, not open-ended**.

**Do not write a new parser.** Two extractors already exist:
- `memsearch transcript <path>` — renders one session's turns; auto-detects the format.
- `extract_conversation_context()` in
  `~/.claude/claude-memory-compiler/hooks/session-end.py` — keeps only `user` and
  `assistant` roles, which is what drops the tool-result bulk.

**Caps for one run** — state which you used in the report:
- window: 14 days unless the user names a wider one
- at most 20 sessions, newest first
- at most ~200 KB of extracted text per session; truncate the middle, keep both ends
- strip `tool_result` blocks before any of it reaches a model

Always trawl in a subagent and return findings only.

**Handling care.** Raw records can quote `PERFORMANCE.md` → `DexaProject/` identifiable
health data. Reading it locally in a subagent is fine; nothing carrying it may be written
out to the vault, a memory file, or this skill's report. Cite the session id and date as
evidence instead of quoting the passage.

## What to hunt for

- **Repeated corrections** → feedback memory or a skill fix
- **Decisions with rationale** → permanent vault note
- **Discovered gotchas** → project memory
- **Workflows that worked** → skill candidate

## Output

Present findings as a checklist: each item = the learning + where it should live (memory tier, vault note, skill edit, new skill). User picks; route each approved item to its destination — use memory-write conventions for memories, capture-insight format for vault notes, write-a-skill for skill changes.

## Rules

- Report before you mutate. Nothing is written until the user approves the checklist items.
- Cite evidence (date, file) for each finding so the user can judge it.
- An empty result is legitimate — don't manufacture learnings to look thorough.

# Brain Audit

Score the second brain, store the score, propose two builds. Then stop.

The point is the **trend**, not any single run. A score that only exists once is
the failure this skill was built to fix: `~/SecondBrain/audits/` held exactly one
report for 45 days before this skill existed.

## Step 1 — measure

```bash
bash ~/.claude/skills/brain-audit/measure.sh
```

Facts only, ~7 seconds. **Never estimate a number this script reports.** If a
value reads `MISSING` or `none`, that is a finding, not an error to work around.

## Step 2 — score the four C's, 25 points each

Anchor every score to a measured number so two runs a month apart are comparable.

| C | What it measures | 25 pts | 13 pts | 0 pts |
|---|---|---|---|---|
| **Context** | Evergreen facts on disk | `USER.md` + `MEMORY.md` under cap, 35+ Tier A memories, `Knowledge/` touched <14d | one file over cap, or `Knowledge/` 14–45d stale | a memory file MISSING, or `Knowledge/` >45d stale |
| **Connections** | Live data arriving | `meeting_sync` <7d, `portfolio_json` <14d, `ledger` <30d | one source 2× its window | two or more sources silent |
| **Capabilities** | Skills that get used | audit-driven builds shipped since last run | skills exist, none exercised | skills installed and never run |
| **Cadence** | What keeps it alive | all launchd jobs `exit=0` **and** `Notes/` <21d | jobs green, `Notes/` 21–45d | `Notes/` >45d, or any job non-zero |

Cadence is scored hardest on `Notes/`, not on the jobs. Every job being green while
synthesis is frozen is the exact failure this system keeps repeating.

## Step 3 — run the three tests

Answer each with evidence from Step 1, and mark pass / warn / fail.

1. **Teammate test.** A teammate asks a question. Would the system answer it faster
   than Eric from memory, with sources? Evidence: is the answer actually filed, or
   still only in his head?
2. **Context-switch test.** Can the work be done from one surface? Evidence: command
   centre and dashboard freshness.
3. **Head-emptying test.** Has a decision been captured, or is it being re-litigated?
   Evidence: open items in `MEMORY.md` "Pending Decisions" with no note behind them.

These shape the narrative. They do not move the number.

## Step 4 — write the report

`~/SecondBrain/audits/brain-audit-YYYY-MM-DD.md`, frontmatter `type: resource`.

Sections: score table (four C's + total) → the three tests → what would make the
agent wrong-answer him today → the two proposed builds.

Then append one row to `~/SecondBrain/audits/_trend.md` (create with a header if
absent):

```
| Date | Context | Connections | Capabilities | Cadence | Total | Headline |
```

## Step 5 — level up: propose exactly two builds

Two. Not twelve. A list of twelve is how the last audit's findings died.

Pick against the lowest-scoring C, and check the proposal against
`user_working-conditions-bottleneck.md` — a build that does not touch the stated
bottleneck is the wrong build.

**Prefer automating an existing manual step over adding a new capability.** Measured
history says anything on a timer survives and anything manual stops within six weeks.

Propose, then stop. Do not build them in the same run.

## Gotchas

- **`Inbox/` freshness proves nothing.** It is cron-fed by `meeting-sync` and grows
  daily whether or not the brain is working. Scoring it green hides the real state.
  `Notes/` and `Drafts/` are the honest signal.
- **The recurring disease: everything with a cron is alive, everything manual is
  frozen.** Found 2026-07-24, still true 2026-09-07 — synthesis restarted after that
  audit (11 → 23 notes) and stopped again five weeks later. Expect this pattern; a
  fix that depends on remembering to run something is not a fix.
- **This skill overlaps two others and must not duplicate them.** `claude-stack-doctor`
  owns plumbing; `improve-system` owns note rot. If a finding is "launchd job failed"
  or "these two notes conflict", hand it off by name instead of re-reporting it.
- **Do not run `ingest-resource` on the report.** It is already in the vault.
- **`days_since` pins both timestamps to 12:00:00.** BSD `date -j -f '%Y-%m-%d'` fills
  unspecified time fields from the clock, so an unpinned version reported the same
  date as 34 days on one line and 35 on the next. Keep the pin.
- **Scoring drift breaks the trend.** If a rubric anchor in Step 2 is changed, note the
  change in `_trend.md` on that row, or the column stops meaning one thing.

# Improve System — Vault Audit

Find rot in the vault and report it. Verification only: this skill proposes, the user disposes.

## Step 0 — read the pending ledger first

`~/.claude/claude-memory-compiler/reports/proposals-pending.md`

Do this **before** scanning. Apply anything marked `approved` (then mark it `applied`),
and re-list every `open` item in this run's report next to the new findings. Append new
findings there as `open`, deduplicating against what is already listed.

Without this step a proposal made in a session that ends is lost, and the next run pays
to rediscover it. The file's header carries the entry format.

**Vault:** `vault_root` in the selected platform config
**Paths:** canonical vault locations live in `~/.claude/skills/_shared/config.<platform>.json` — load it if unsure; if a literal path here ever disagrees, the config wins.

Scan `Notes/`, `Knowledge/`, `Projects/` (skip `Archive/`, `Inbox/`, `morning-briefings/`).

1. **Stale**: `status: seed` notes older than 60 days; `Project_*.md` files untouched 30+ days that read as active.
2. **Conflicting**: notes asserting opposing claims on the same domain/tags — compare titles and opening claims, read bodies only for suspected pairs.
3. **Duplicates**: near-identical titles or same core concept under different slugs.

Output a short report grouped by issue type with a proposed action per item (merge / archive / update status / no action). **Apply nothing until the user picks.** Archive = move to `Archive/`, never delete.
