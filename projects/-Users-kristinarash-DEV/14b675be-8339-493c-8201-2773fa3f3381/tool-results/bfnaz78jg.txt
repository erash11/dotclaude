    32	The `daily-backup` job is in that registry with `reconcile: true`, `graceMinutes: 60`,
    33	`maxAttemptsPerDay: 2`, and `makeupWindow: 07:00-20:00`. Its `successProbe` greps today's
    34	`daily-backup.log` for `daily-backup end: OK`. So:

    37	- **launchd `com.keystone.dailybackup` fires at 09:00 regardless** → the second run.
    38	- **Run the backup by hand before 07:00 and reconcile skips it** ("already succeeded today").
    39	  Confirmed 09-03: a 06:15 manual run logged `OK` at 06:25, and no 07:00 run happened.

    43	`at` has not bitten yet. Still true: `launchctl ... runs = 0` proves nothing — read the log.

   115	## Traps that cost time
   116	
   117	- **Milvus is NOT in the memsearch path**, despite what `RESTORE.md` and the Bucket docs
   118	  say. Indexing works with port 19530 closed and Docker not installed. Don't set it up.
   119	- **`-DryRun` cannot verify a write path.** It passes `rsync -n`, which writes nothing. A
   120	  snapshot that fails live will show `OK` in a dry run. Only a non-dry run is evidence.
   121	- **Never size up a DriveFS destination with `du`.** It reports local cache/allocated
   122	  blocks, not logical size — the `codex/sessions` mirror read as "47 MB of 289 MB" while
   123	  actually holding 255 of 256 files, with a 35 MB file verified byte-identical by
   124	  `stat -f%z` on both sides. Compare **file counts and per-file byte sizes**, never `du -sh`.
   125	- **`snapshot:sessions` is a genuine hang** — not a size problem, not a lock, not a
   126	  permission fault, and not slow enumeration. Three wrong theories died here in one
   127	  session; see the evidence section below before forming a fourth. **Bounded 2026-08-14**
   128	  by a watchdog in `Invoke-Rsync` (900s ceiling, hard SIGKILL, records `rsync-timeout`),
   129	  committed as `8863a37`. That caps the symptom so the run reaches the SSD capture. The
   130	  wedge itself is still unexplained.
   131	- **Tier A memory is NOT in git.** `~/.claude/.gitignore` line 1 is `/*` (default-deny
   132	  allowlist) and `projects/` is not allowlisted, so `projects/*/memory/*.md` has exactly
   133	  two backup layers: the Drive SNAP of `~/.claude/projects`, and the SSD. With CRASHBOX
   134	  unmounted that is a single copy. Nothing to "commit" there — it's by design.
   135	- **`daily-backup.ps1` refuses to merge diverged repos by design** — that's correct
   136	  behavior, not a bug. Reconcile by hand.
   137	- **stack-doctor's cloud heartbeat** watches the newest per-run receipt
   138	  (`_receipts/run-*.txt`). It used to watch `RESTORE.md`, which the job *copies*
   139	  (`Copy-Item -Force`, line 411) rather than rewrites, so its mtime never advanced and the
   140	  check cried `backup-cloud-stale (218h)` while DriveFS was healthy. Fixed 2026-08-14.
   141	- **Untracked files block a fast-forward**, and plain `git stash` does not pick them up —
   142	  needs `-u`, or rename them aside. Bit the documented SecondBrain fix.
   143	- Reading exit codes through a pipe returns the *last* pipeline element's status, not the
   144	  command's — see [[zsh-shell-traps]]. This produced two wrong readings in one
   145	  session (`rsync ... | tail` and a stack-check run).

   189	## `snapshot:sessions` — evidence from a live reproduction, 2026-08-14 15:20 (stack-doctor)
   190	
   191	Caught the hang in progress and narrowed it. **Root cause still open** — this section is
   192	evidence, not a verdict. Everything below is measured, not inferred:
   193	
   194	- **It is a hang, not a slow transfer.** Four rsync processes (client `-a ... codex/sessions/`,
   195	  its `--server` receiver, plus two older receivers) sat at **0.01–0.03 s of CPU across
   196	  34–85 minutes** of wall clock. Zero progress, not slow progress.
   197	- **Nothing is left to copy.** The mirror is **256/256 files** — the previously-missing
   198	  `2026/08/06/rollout-*.jsonl` is present. A complete mirror still hangs.
   199	- **The mount is healthy.** A recursive `find` over the destination returned 256 files
   200	  promptly, and `touch` inside the exact hung directory succeeded instantly. Reads *and*
   201	  writes both work, so this is not a wedged DriveFS/FUSE mount.
   202	- **The wedged processes ignore SIGTERM** (still alive minutes later in `S` state) — they
   203	  are blocked inside a call that neither returns nor delivers signals.
   204	- **Dry runs cannot see it**: `-n` completes clean, live runs hang. Another instance of the
   205	  "`-DryRun` cannot verify a write path" trap above.
   206	
   207	### Orphans are a symptom, not the cause
   208	
   209	Two `rsync --server` receivers were **orphaned to PPID 1** (started 13:55 and 14:33). It is
   210	tempting to call them the blocker; the timeline refutes it — the **10:31:54 run hung at the
   211	identical point** (last line `SNAP skip (missing): .codex/memories`, no end line) while the
   212	oldest surviving orphan did not exist until 13:55. `kill` on both orphans did not unblock
   213	the live pair either.
   214	
   215	Why they accumulate: **`daily-backup.ps1` contains no `pkill` at all** (verified by grep —
   216	do not go looking for one). The anchored `pkill -f "^/usr/bin/rsync"` belongs to an *ad-hoc
